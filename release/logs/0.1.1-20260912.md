## 2. client 公钥表：为什么搬、搬到哪

### 2.1 问题

`auth.clients` 原先写在 profile 的 `cordis.patch.yml` 里，而该文件是**冷配置**——
实测改它不会热生效（改端口不搬、无重激活日志），必须重启。但 client 是**业务配置**：
每接入一个业务系统就停一次服，不合理。

### 2.2 目录形态

```
<runtime>/clients/
├─ clients.json          [{ "clientId": "...", "scope": [...], "enabled": true }]
└─ <clientId>.pem        该 client 的公钥（SPKI PEM，整段原文）
```

*   **为什么 JSON 而不是 YAML**：插件零运行时依赖，没有 YAML 解析器；`JSON.parse` 内置。
*   **为什么公钥单独放 `.pem`**：JSON 里 PEM 只能写成带 `\n` 的单行转义字符串，
    那正是运维最容易贴错的形式；独立文件让公钥保持整段原文、零转义。
*   **为什么不借用 DSH 的 `ctx.settings`**：那会把"信任根存在哪、什么格式、怎么校验"
    绑到上游结构上，而上游怎么变不可控。这里用插件自有的目录与格式，自足。

### 2.3 语义

| 行为 | 结果 |
|---|---|
| 新增/修改 client | 下一个轮询周期（约 2s）生效，**不重启** |
| `enabled: false` | 停用该 client —— **废止路径**，不必删文件 |
| `clients.json` 解析失败 | **保留上一份可用集合**只记警告 —— 一个笔误不该把所有人锁在门外 |
| `clients.json` 合法但为空 | 生效为空集（fail-closed：全部 API 401，静态页可达） |
| `clientId` 非法/重复、`scope` 未知、缺 `.pem` | 跳过该条并记问题，不影响其余 client |

`clientId` 限 `[A-Za-z0-9_-]{1,64}`：它会被拼进内部 session id 与 `workspace/<clientId>/`
目录名，收敛字符集同时是路径穿越防护。

### 2.4 实现要点

*   轮询（2s）而非 `fs.watch`：Windows 上编辑器普遍"写临时文件再改名"，watch 会丢事件；
    目录里只有一个小 JSON 与若干 `.pem`，`stat` 成本可忽略。
*   变更即 `SignatureVerifier.reload()` **就地换集合**，不重建插件。

## 3. 交付面：两个启动器

| 脚本 | 定位 |
|---|---|
| `dsh-biz-bridge.cmd` / `.sh` | 启动桥服务。**一键**：无参数时自行完成首次安装、升级重装、配置播种 |
| `dsh-web.cmd` / `.sh` | 启动**包内这套 DSH** 的浏览器面（`--profile web`，端口 **42730**），用于配置模型与凭据 |

两者用同一套约定：**包内 Node + 包内 CLI + `DSH_HOME=<包根>/runtime`**，与机器上既有的
DSH 安装完全隔离。因此 `web` 与 `bizbridge` 两个 profile 共享同一份 `settings.yaml`
与 `.credentials.yaml` —— 在 web 里配的模型，桥服务直接读得到。

> ⚠️ **安全提示**：`dsh-web` 装载的是 `dsh-base`，其中含 bash / pwsh / 文件系统 / 沙箱，
> 因此它同时会暴露一个 agent 操作台。它只监听 `127.0.0.1`，**用完应关闭**。

## 5. 升级指引

替换 `program/`，`runtime/` 原地保留，然后**重新运行 `dsh-biz-bridge.cmd`**——
脚本会比对 profile 里记录的插件包名与随包 tgz 名称，不一致就自动重装，也不会碰你改过的配置。

**client 无需手工迁移**：首次激活时若 `clients/` 下还没有 `clients.json`，
插件会把 composition 配置里原有的 `auth.clients` 落成目录形态并记一行日志；
之后请改 `runtime/clients/`（**改动即时生效，不再需要重启**）。
